# Embodied Control Agent Report

## 1. 研究目标

本课题的目标是将“视觉时序表征模型”重新接回强化学习任务，构建一个能够在线感知、持续记忆并实时控制的小车接球智能体，而不是传统的“observe then act”式离线预测模型。

具体来说，目标包含三层：

1. 保留已有视觉时序模型中对球体运动连续性的表征能力。
2. 在不引入球的 privileged vector 输入的前提下，将模型改造成可用于闭环控制的 agent。
3. 在 Unity + ML-Agents 的强化学习环境中训练该 agent，使其能够稳定完成接球任务。

本项目最终采用了一条“离线表征预热 + 在线强化学习微调”的技术路线。

## 2. 任务环境与问题设定

### 2.1 环境任务

环境中的任务是让一辆小车移动到球的落点位置，并在球落地前用车上的接球区域完成接球。环境实现位于：

- `ball_fetch/Assets/CarCatcherAgent.cs`
- `ball_fetch/Assets/CatchCarScene_basket_0309.unity`

训练与推理使用的行为名为 `CarCatch`。

### 2.2 动作定义

动作是二维连续控制：

- `a_0`: 前后方向目标速度指令
- `a_1`: 左右方向目标速度指令

在环境中，动作不是加速度，而是直接映射为平面目标速度。因此，agent 的“上一动作”与“当前自速度”在物理意义上高度相关。基于这一点，最终设计中没有把 `prev_action` 作为独立输入，而是只保留了车体自身平面速度作为本体感觉输入。

### 2.3 观测设定

本课题特别强调“非特权输入”：

- 保留视觉输入
- 保留车的自身速度
- 不将球的位置、速度等 privileged vector 直接作为 policy 输入
- 不将车的世界坐标位置作为 policy 输入

在 Unity 环境中，这一设置对应于：

- `useVectorObs = false`
- `useSelfVelocityObs = true`

因此，在线强化学习阶段，agent 的输入主要由两部分组成：

1. 相机视觉观测
2. 车体自身平面速度

### 2.4 奖励函数

当前奖励由以下几部分组成：

- 接近球体的精度项
- 接近落点的进度项
- 控制代价
- 动作平滑代价
- 成功接球奖励
- 接球失败惩罚
- 出界惩罚

其中，终止奖励设置为：

- `catchReward = +50`
- `missReward = -50`

从实现上看，环境并不是一个完全“只在终点给奖励”的极端稀疏奖励任务，而是一个带有 shaping 项的半稀疏任务。这也是后续模型能够较快收敛的重要原因之一。

## 3. 从落点预测模型到具身控制模型

### 3.1 原有模型的问题

在前期实验中，已经有一条较成熟的 `landing_world_model` 路线。它的核心能力是：

- 观察轨迹前半段
- 利用视觉时序模型提取运动信息
- 预测球的最终落点

该路线对于“未来运动理解”很有效，但它仍然是一个监督学习式的离线落点预测器，不是一个真正的在线控制 agent。它主要有三个限制：

1. 任务目标是预测落点，而不是控制动作。
2. 输入不包含 agent 自身状态。
3. 模型使用方式更接近“先观察，再输出一个结果”，而不是逐步更新内部状态并实时决策。

### 3.2 新模型的设计思想

新模型的核心思想是：把已有的短时视觉运动编码能力，升级为一个能服务于在线控制的具身时序智能体。

设计原则如下：

1. 视觉仍然承担“看见球如何运动”的职责。
2. 自身速度承担“当前身体状态”的职责。
3. 长时记忆承担“把到目前为止看到的轨迹趋势积累起来”的职责。
4. 动作头同时读取最新短时视觉与长时记忆，避免只靠历史或只靠瞬时反应。

## 4. 模型结构

模型定义位于：

- `temperal/experiments/embodied_control/src/models/embodied_recurrent_policy.py`
- `rl_be/experiments/exp_ec_0001/train_embodied.py`

### 4.1 时间建模策略

本课题采用如下时间建模单位：

- 局部视觉窗口长度：`8` 帧
- 局部视觉步长：`4` 帧
- 控制更新周期：每 `4` 帧更新一次动作

这意味着每个局部视觉 token 覆盖两个控制周期，而 policy 本身每个控制周期输出一次动作。

### 4.2 输入组成

每个控制时刻输入：

1. 最近 `8` 帧构成的局部视觉窗口
2. 当前窗口末尾的车体平面速度

其中速度只取一个时刻，而不是整段序列。这是因为在当前环境中动作每 `4` 帧更新一次，并在这段时间内保持恒定，因此窗口末尾的速度已经足以代表该控制周期的自身状态。

### 4.3 模块划分

模型由以下部分组成：

#### (1) 短时视觉模块

短时视觉模块复用了已有的多尺度视觉动力学结构：

- `MultiScaleEncoder`
- `MultiScaleDynamics`

其作用是把最近 `8` 帧图像编码成一个短时运动 token，记为 `z_short_t`。

#### (2) 自身状态模块

车体自身速度通过一个小型 MLP 编码为 `z_self_t`。该分支只输入自速度，不输入球体的 privileged vector，也不输入车的绝对位置。

#### (3) 记忆融合模块

将 `z_short_t` 与 `z_self_t` 融合后，得到记忆输入 token：

`z_mem_t = fuse([z_short_t, z_self_t])`

#### (4) 长时记忆模块

使用 `GRU` 维护长时内部状态：

`h_long_t = GRU(z_mem_t, h_long_{t-1})`

它负责累积整段观测过程中的轨迹信息。

#### (5) 动作头与价值头

动作头与价值头都读取：

- 最新的短时视觉表征 `z_short_t`
- 当前长时记忆 `h_long_t`
- 当前自身状态表征 `z_self_t`

因此，动作输出并不是只依赖记忆，也不是只依赖当前一眼的视觉，而是同时依赖：

- 当前看到了什么
- 到现在为止积累了什么
- 自己现在怎么动

### 4.4 架构意义

该设计体现了明显的“具身控制”风格：

- 视觉模块负责外界信息
- 自速度模块负责本体感觉
- 记忆模块负责跨时整合
- 动作头负责把“外界 + 身体 + 记忆”融合成控制

这比单纯将状态向量直接拼接到最后一层更符合课题目标，也更适合作为毕设中的模型创新点。

## 5. 参数复用与初始化策略

### 5.1 复用来源

新模型并不是完全从零开始训练，而是尽量复用了已有的时序视觉参数。初始化来源为：

- `landing_world_model` 中的 hierarchical 模型

具体复用模块包括：

- `encoder`
- `dynamics`
- `token_proj`
- `long_gru`（在结构兼容时）

不复用的部分主要包括：

- 落点预测 head
- 强化学习的 policy/value 读出头

### 5.2 冻结策略

训练初期采用了如下策略：

- 冻结局部视觉 encoder
- 允许 dynamics 尽早参与适配
- 从一开始训练新的 self-state encoder、memory fuse、policy head、value head

这种策略的动机是：

1. 保持已有视觉低层特征的稳定性。
2. 让短时动力学逐步适应闭环控制任务。
3. 让新引入的具身控制接口尽快建立作用。

## 6. 离线预热方法

### 6.1 为什么需要离线预热

如果直接用 PPO 从零训练“视觉 + 时序记忆 + 连续控制”的网络，通常会面临：

- 视觉特征学习太慢
- 记忆单元学不到有效信息
- 稀疏或半稀疏奖励下探索效率低

因此，本课题先使用离线数据对模型表征进行预热，再进入在线强化学习。

### 6.2 数据采集方式

离线数据不是人工手工控制采集，而是通过 Unity 内部构建的一个匀速拦截启发式控制器自动生成。

启发式控制器定义在：

- `ball_fetch/Assets/LandingInterceptHeuristic.cs`

其核心逻辑是：

1. 利用环境中已知的球落点和剩余飞行时间。
2. 先在飞行前半段保持静止。
3. 在后半段按照“剩余位移 / 剩余时间”计算所需速度。
4. 输出可直接作用于车体的速度控制指令。

这种轨迹相较于“全程匀速追落点”更适合作为视觉时序预热数据，因为它保留了球在视野中明显偏移、变化和靠近的过程。

### 6.3 数据规模

采集得到的数据集路径为：

- `ball_fetch/vis_backbone/datasets/manual_capture/20260401_101517`

数据规模如下：

- 轨迹总数：`1000`
- 训练集：`800`
- 验证集：`100`
- 测试集：`100`

### 6.4 数据格式

由 `TrajectorySampler.cs` 采样的每条轨迹包含：

- 图像帧序列
- 当前动作
- 车的位置与速度
- 球的位置与速度
- 预测落点
- 预测落地时间

但在离线预热时，遵循“特权信息只作为训练目标，不作为输入”的原则：

- 输入：图像窗口 + self velocity
- 监督目标：落点偏移、剩余飞行时间等

### 6.5 预热任务

离线预热主要训练的是：

1. 相对落点偏移预测
2. 剩余落地时间预测

这相当于给模型一个自上而下的监督信号，让它学习：

- 球会落到哪里
- 还剩多久会落地

虽然这些信号在部署时不会作为输入提供给 agent，但它们有助于塑造一个对未来运动更敏感的内部表征。

### 6.6 预热结果

预热结果保存在：

- `temperal/experiments/embodied_control/output/offline_warmup_manual_capture_20260401_101517/summary.json`

关键指标如下：

| 指标 | 数值 |
|---|---:|
| 最优 epoch | 18 |
| 最优验证损失 | 0.3834 |
| 验证集落点 L2 | 0.5065 |
| 验证集时间 MAE | 0.0502 |
| 测试集总损失 | 0.3103 |
| 测试集落点 L2 | 0.4756 |
| 测试集时间 MAE | 0.0518 |

这说明离线预热阶段已经学到了较稳定的短时视觉-运动表征。

## 7. 在线强化学习训练方法

### 7.1 强化学习框架

在线训练使用 Unity ML-Agents 的 PPO 算法，训练入口位于：

- `rl_be/experiments/exp_ec_0001/train_embodied.py`

该脚本并没有沿用 ML-Agents 默认的视觉网络，而是：

1. 注册自定义的 `EmbodiedActor`
2. 注册自定义的 `EmbodiedValueNetwork`
3. 在 PPO 外壳内复用我们自己的 PyTorch 模型

ML-Agents 在这里负责的是：

- 与 Unity 通信
- 采样经验
- PPO 更新
- 日志与 checkpoint 管理

真正的感知、记忆和动作计算，仍然是我们自己实现的模型。

### 7.2 PPO 训练配置

正式训练配置位于：

- `rl_be/experiments/exp_ec_0001/config/ppo_embodied_recurrent.yaml`

关键超参数如下：

| 参数 | 数值 |
|---|---:|
| batch_size | 512 |
| buffer_size | 20480 |
| learning_rate | 3e-4 |
| num_epoch | 10 |
| gamma | 0.99 |
| hidden_units | 128 |
| num_layers | 2 |
| memory.sequence_length | 16 |
| memory.memory_size | 64 |
| checkpoint_interval | 50000 |
| max_steps | 500000 |
| summary_freq | 5000 |

### 7.3 训练环境

在线训练使用的 build 为：

- `ball_fetch/build/e2_360_0_6/ball_fetch.exe`

后续也支持将训练好的模型接回 Unity Editor 做在线推理观察。

### 7.4 ONNX 导出问题与处理

在训练过程中发现，ML-Agents 在 checkpoint 时会尝试额外导出 ONNX 模型。但对于当前自定义 embodied actor，这一步并不稳定，容易在 checkpoint 附近导致主 trainer 退出，随后所有 worker 报出 `BrokenPipe / EOFError`。

为保证训练稳定性，在当前实验分支中已将训练时自动 ONNX 导出关闭。这不会影响 PyTorch checkpoint 的保存与恢复，也不会影响继续训练，只会暂时影响“导出 Unity 内嵌推理模型”的流程。

## 8. 训练效果

### 8.1 早期阶段

在 `temp_realTime_0001` 这条正式 run 中，早期训练表现如下：

| Step | SuccessRate | Cumulative Reward |
|---|---:|---:|
| 50000 | 0.2621 | -21.3647 |

这说明在早期阶段，模型虽然已经开始学习有效行为，但成功率仍然有限。

### 8.2 中后期阶段

在后续训练中，性能显著提升：

| Step | SuccessRate | Cumulative Reward |
|---|---:|---:|
| 355000 | 1.0000 | 71.0463 |
| 360000 | 1.0000 | 71.6126 |

同时：

- Episode Length 基本稳定在约 `33.4`
- Policy Entropy 下降到约 `1.20`
- Value Loss 从早期的大值下降到较低水平

这些现象说明：

1. agent 已不再依赖高随机性探索。
2. 策略逐渐收敛为稳定接球行为。
3. 价值估计与策略学习均明显优于训练初期。

### 8.3 定性观察

在 Unity Editor 中加载训练好的 checkpoint 进行推理观察后，可以看到：

- 小车能够稳定判断球的落点趋势
- 控制行为平滑
- 接球成功率很高
- 行为表现出明显的“先观察、再移动并调整”的特征

这说明当前模型并不是仅仅记住某个固定轨迹，而是确实形成了可用于闭环接球的策略。

## 9. 结果分析与讨论

### 9.1 为什么这条路线有效

本课题取得有效训练结果，主要可能有以下几个原因：

#### (1) 视觉时序表征被成功迁移

已有视觉时序模型已经具备对球体运动连续性的建模能力。通过参数复用与离线预热，这种能力被较顺利地转移到了在线控制任务中。

#### (2) 自身状态输入方式合理

只输入 self velocity 而不输入球的 privileged vector，既保持了任务设定的“非特权性”，又给了策略最必要的本体感觉信息。

#### (3) 动作头同时读取短时与长时信息

动作读出同时使用 `z_short` 与 `h_long`，使得策略能够兼顾：

- 对当前视觉变化的快速反应
- 对整段轨迹趋势的累积判断

#### (4) 奖励虽非完全稀疏，但足够支持闭环学习

当前环境包含落点进度、精度与终止奖励等 shaping 项，使得 PPO 更容易为时序模型提供学习信号。

### 9.2 本模型学到的可能机制

从行为上推测，当前 agent 很可能学会了以下几类内部能力：

1. 利用短时视觉估计球当前运动趋势。
2. 利用长时记忆累积对落点和到达时机的判断。
3. 利用自身速度调节控制输出。
4. 在球的前半段主要观察，在后半段做拦截控制。

这与课题最初提出的“具身时序控制”目标是高度一致的。

### 9.3 限制

目前仍有几个局限需要在报告中如实说明：

1. 目前对模型内部表征的解释还不充分。  
   虽然行为已经很好，但还需要进一步研究 `z_short` 与 `h_long` 的信息内容。

2. 训练结果主要在当前任务分布上验证。  
   还需要更多跨随机种子、跨发球分布的泛化验证。

3. ONNX 导出尚未完全解决。  
   当前训练稳定性已可保证，但部署型导出还需额外处理。

4. 当前速度仍然较慢。  
   actor 与 critic 各自维护一套 embodied feature body，且模型内部存在双重时序循环，因此计算开销较大。

## 10. 可作为毕设贡献的表述

从毕设写作角度，本课题可以概括出以下几项贡献：

### 贡献 1：提出了一种从离线落点预测模型迁移到在线具身控制 agent 的方法

该方法不是简单替换输出头，而是系统地重构了：

- 输入结构
- 时序记忆结构
- 强化学习接口

使其能够从“落点预测器”转化为“在线接球控制器”。

### 贡献 2：构建了非特权输入下的具身控制架构

模型仅依赖：

- 视觉
- 自速度

而不依赖球的位置和速度等 privileged state，体现了较强的任务真实性与方法约束。

### 贡献 3：设计了离线预热与在线强化学习结合的训练范式

通过：

1. 启发式生成轨迹。
2. 使用落点/时间目标进行表征预热。
3. 再接入 PPO 微调。

显著提升了训练可行性和最终性能。

### 贡献 4：在 Unity 接球任务中验证了该架构的有效性

实验表明，最终 agent 能够在当前任务中稳定实现高成功率接球，并在编辑器观察中表现出合理而平滑的闭环行为。

## 11. 后续工作建议

基于当前结果，后续最有价值的研究方向包括：

1. 解释性分析。  
   提取并可视化 `z_short`、`z_self`、`h_long` 与动作之间的关系。

2. 消融实验。  
   分别去掉短时直连、长时记忆、自速度输入，分析性能变化。

3. 泛化测试。  
   在不同随机种子、不同发球参数分布下验证鲁棒性。

4. 训练加速。  
   尝试共享 actor/critic 的 feature body，或减少时序展开开销。

5. 导出与部署。  
   解决 ONNX 导出问题，实现更标准的 Unity 侧部署推理流程。

本课题完成了从“视觉落点预测模型”到“具身时序强化学习控制 agent”的系统改造，并在 Unity 接球任务中获得了稳定有效的结果。

- 非特权输入设计
